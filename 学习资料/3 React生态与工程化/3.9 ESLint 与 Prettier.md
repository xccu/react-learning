# ESLint 与 Prettier 详解：代码规范与格式化

---

## ESLint 与 Prettier 的定义

ESLint 是 JavaScript 的代码质量静态检查工具，负责检查代码中可能存在的错误、不符合最佳实践的写法以及潜在的 bug。Prettier 是代码格式化工具，负责统一代码的外观风格（引号、分号、缩进、换行等）。ESLint 查"对错"，Prettier 管"外观"，两者配合使用可以同时保证代码的质量与一致性。

**核心特点：**
- ESLint 提供可插拔的规则系统，支持通过配置灵活开启、关闭或自定义规则
- Prettier 自动格式化代码，无需人工记忆风格规范，团队协作时风格天然统一
- 两者均支持命令行执行，可与编辑器、CI 流程深度集成

**官方文档链接：**
- [ESLint 官方文档](https://eslint.org)
- [Prettier 官方文档](https://prettier.io)

如果追求极致的检查速度，可以了解 oxlint，它是基于 Rust 实现的更快的 JavaScript lint 工具，规则兼容 ESLint 生态，可作为 ESLint 的高性能替代方案。

## ESLint 与 Prettier 基本用法

### 1. 安装依赖

```bash
npm install -D eslint @eslint/js typescript-eslint eslint-plugin-react-hooks prettier eslint-config-prettier
```

- **eslint**：ESLint 核心包，负责静态检查
- **@eslint/js**：ESLint 官方推荐的 JavaScript 基础规则集
- **typescript-eslint**：TypeScript 的解析器与规则集，让 ESLint 能检查 TS 代码
- **eslint-plugin-react-hooks**：React Hooks 规则插件，检查 Hooks 使用是否规范
- **prettier**：代码格式化工具
- **eslint-config-prettier**：关闭 ESLint 中与 Prettier 冲突的格式类规则，避免两套规则打架

### 2. ESLint 配置文件

在项目根目录创建 `eslint.config.mjs`（新版扁平配置格式）：

```js
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import reactHooks from 'eslint-plugin-react-hooks';

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ['**/*.{ts,tsx}'],
    plugins: { 'react-hooks': reactHooks },
    rules: {
      'react-hooks/rules-of-hooks': 'error',
      'react-hooks/exhaustive-deps': 'warn',
      'no-unused-vars': 'error',
    },
    ignores: ['node_modules/**', 'dist/**'],
  },
];
```

- **规则配置**：`'no-unused-vars': 'error'` 未使用的变量会报错
- **Hooks 规则**：`'react-hooks/rules-of-hooks': 'error'` 违反 Hooks 调用规则时报错
- **依赖检查**：`'react-hooks/exhaustive-deps': 'warn'` 检查 useEffect 等 Hooks 的依赖数组是否完整
- **忽略配置**：`ignores` 跳过 node_modules 和 dist 目录，避免检查第三方代码与构建产物
- **配置合并**：`export default [...]` 多个配置对象按顺序合并，后者覆盖前者

### 3. Prettier 配置文件

在项目根目录创建 `prettier.config.mjs`：

```js
/** @type {import('prettier').Config} */
const config = {
  printWidth: 100,
  tabWidth: 2,
  semi: true,
  singleQuote: true,
  trailingComma: 'es5',
  arrowParens: 'always',
};

export default config;
```

- **printWidth**：每行最大宽度，超过 100 字符自动换行
- **tabWidth**：缩进宽度为 2 个空格
- **semi**：`true` 表示语句末尾保留分号
- **singleQuote**：`true` 表示优先使用单引号
- **trailingComma**：`'es5'` 表示在 ES5 允许的位置添加尾逗号
- **arrowParens**：`'always'` 表示单参数箭头函数也保留括号，如 `(x) => x`

### 4. 运行检查与格式化

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "format": "prettier --write ."
  }
}
```

```bash
npx eslint src/App.tsx        # 检查单个文件
npx eslint . --fix            # 检查并自动修复可修复的问题
npx prettier --write src/     # 格式化 src 目录下所有文件
```

- **lint 脚本**：`eslint .` 检查当前目录下所有源代码文件
- **lint:fix 脚本**：`eslint . --fix` 自动修复可自动修复的问题（如未使用变量、格式问题）
- **format 脚本**：`prettier --write .` 用 Prettier 格式化所有文件并直接写入
- **命令组合**：在 `lint-staged` 中组合执行，可在提交前自动完成检查与格式化

### 5. 常见规则示例

React Hooks 规则要求 Hooks 调用必须在组件的顶层，不能在条件、循环或嵌套函数中调用：

```tsx
// 错误：在条件中调用 Hooks
function BadCounter({ enabled }: { enabled: boolean }) {
  if (enabled) {
    const [count, setCount] = useState(0);  // 违反 rules-of-hooks
    return <button onClick={() => setCount(count + 1)}>{count}</button>;
  }
  return <span>禁用</span>;
}

// 正确：Hooks 始终在顶层调用
function GoodCounter({ enabled }: { enabled: boolean }) {
  const [count, setCount] = useState(0);

  if (!enabled) {
    return <span>禁用</span>;
  }
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- **顶层调用**：`useState` 必须位于组件函数的最顶层，保证每次渲染调用顺序一致
- **条件渲染后置**：将条件 return 放在 Hooks 调用之后，Hooks 仍保持顶层调用
- **调用顺序**：React 依赖 Hooks 的固定调用顺序来对应状态，顺序变化会导致状态错乱

## 常见陷阱与最佳实践

### 1. ESLint 与 Prettier 规则冲突

```js
// 冲突场景：ESLint 要求分号，Prettier 移除分号
// 未配置 eslint-config-prettier 时，两边互相覆盖，保存后不断报错

// eslint.config.mjs
import js from '@eslint/js';
import prettier from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  prettier,  // 放在最后，关闭所有与 Prettier 冲突的格式规则
];
```

- **冲突根源**：ESLint 与 Prettier 都可能管理分号、引号等格式，规则重叠时互相冲突
- **解决方式**：用 `eslint-config-prettier` 关闭 ESLint 的格式类规则，格式交给 Prettier，ESLint 只负责代码质量
- **配置顺序**：prettier 配置必须放在最后，才能覆盖前面的冲突规则

### 2. 忽略文件配置缺失

```bash
# 错误：没有忽略配置，ESLint 和 Prettier 会遍历 node_modules 和 dist
npx eslint .          # 扫描 node_modules，耗时巨大且报告大量第三方问题
npx prettier --write . # 格式化 node_modules，可能破坏依赖

# 正确：.eslintignore 或 .prettierignore 中排除目录
node_modules
dist
build
coverage
```

- **忽略文件**：`.eslintignore` 与 `.prettierignore` 分别控制两个工具的扫描范围
- **必须忽略**：`node_modules`、`dist`、`build`、`coverage` 等目录应始终忽略
- **性能影响**：缺少忽略配置会导致全量扫描，检查变慢且产生大量无效报错

### 3. Hooks 规则违反

```tsx
// 错误：在循环中调用 Hooks，渲染次数变化时状态会错乱
function BadList({ items }: { items: string[] }) {
  return items.map((item) => {
    const [selected, setSelected] = useState(false);  // 违反 rules-of-hooks
    return <button onClick={() => setSelected(!selected)}>{item}</button>;
  });
}

// 错误：在 useEffect 内部调用 Hooks
function BadEffect({ id }: { id: number }) {
  useEffect(() => {
    const data = useState(null);  // 违反 rules-of-hooks
    fetchData(id).then(setData);
  }, [id]);
}
```

- **循环内调用**：在循环、条件、嵌套函数中调用 Hooks 都违反 `rules-of-hooks`
- **修复思路**：把状态提升到组件顶层，或拆分成独立的子组件
- **插件的意义**：`eslint-plugin-react-hooks` 能在开发阶段自动提示这类问题，避免运行时的诡异 bug

### 4. 最佳实践

1. **先装 Prettier 再装 ESLint**，用 `eslint-config-prettier` 消除两者冲突，让工具各司其职
2. **把 lint 与 format 接入 pre-commit 钩子**（配合 husky 与 lint-staged），确保合入仓库的代码已经过检查
3. **忽略配置写在文件里**，用 `.eslintignore`、`.prettierignore` 或配置文件中的 `ignores` 字段排除无关目录
4. **将 `lint:fix` 作为日常默认命令**，让 ESLint 自动修复可修复的问题，减少手工改动
5. **不要手动 `--disable` 规则**，除非有明确理由并添加注释说明，避免规则形同虚设
6. **保持 `printWidth` 与缩进统一**，全组使用同一份 Prettier 配置，杜绝格式化争议

## 总结

ESLint 与 Prettier 是前端工程化的基石，共同保障了代码质量与风格一致：

- **分工明确**：ESLint 查"对错"（质量与规则），Prettier 管"外观"（格式与风格）
- **工程化集成**：通过 npm 脚本、CI 与 git 钩子实现自动检查，无需人工把关
- **冲突可解**：`eslint-config-prettier` 关闭重叠规则，两套工具协同而不打架
- **Hooks 强约束**：`react-hooks/rules-of-hooks` 在编译前拦截违规调用，降低运行时风险
- **性能考量**：配置忽略目录、选用 oxlint 等方案可以显著加快检查速度
